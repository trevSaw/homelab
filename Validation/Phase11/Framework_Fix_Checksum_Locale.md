# Framework Fix — Locale-Dependent Checksum Verification

**Date:** 2026-07-31  
**Component:** `scripts/migration/verify-service.sh`, `scripts/migration/lib/common.sh`  
**Severity:** High — verification gate produced false failures on trees containing non-ASCII filenames  
**Status:** **RESOLVED** (regression-tested)

## Symptom

Phase 11 Jellyfin verification failed with a single opaque warning:

```
WARN: Checksum inventory differs
ERROR: Verification failed for jellyfin
```

while every independent signal said the copy was perfect:

| Signal | Result |
|---|---|
| Source vs dest file count | 48,104 = 48,104 |
| Source vs dest directory count | 22,722 = 22,722 |
| Byte delta | ~2 MB on 11 GB (inside 1% threshold) |
| `rsync -n --checksum` | no content transfers required |
| Manual set comparison of inventories | identical |
| `cmp` on the file the diff pointed at | identical |

## Root cause

The old comparison was:

```bash
(cd "$SVC_SOURCE" && find . -type f -print0 | sort -z | xargs -0 cksum) >"$TMPA"
(cd "$SVC_TARGET" && find . -type f -print0 | sort -z | xargs -0 cksum) >"$TMPB"
diff -q "$TMPA" "$TMPB"
```

Two independent defects combine:

**1. `sort` ran under the operator's ambient locale.** The host runs `LC_COLLATE=en_US.UTF-8`. glibc's UTF-8 collation is **not a total order** over filenames: characters with no collation weight defined for the locale — Hangul syllables, Kana, emoji, some accented Latin — compare **equal** to one another. Demonstrated on this host:

```console
$ printf '%s\n' '이정훈' '김융희' | sort -u | wc -l
1                      # glibc considers these two names EQUAL
$ printf '%s\n' '이정훈' '김융희' | LC_ALL=C sort -u | wc -l
2                      # byte order keeps them distinct
```

**2. When names tie, `sort` preserves input order** — and input order comes from `readdir()`, which differs between filesystems. The source is ZFS (`/hive`), the destination is btrfs (`/mnt/monarch`). The same two names are therefore emitted in opposite order on each side:

```console
$ printf '%s\0' './이정훈.jpg' './김융희.jpg' | sort -z | md5sum
3278295559f2afc9277fc30e738995a4
$ printf '%s\0' './김융희.jpg' './이정훈.jpg' | sort -z | md5sum
938d483ce4cdbb02da0adc0a41344227      # different, same input set
```

**3. `diff -q` is positional.** Two inventories holding identical records in different line order are reported as different.

Jellyfin's `data/metadata/People/` tree holds thousands of Hangul, Kana and accented Latin actor names, so the collision was effectively guaranteed. The real diff was exactly two swapped lines out of 48,104:

```diff
-4048988276 50863 ./data/metadata/People/이/이정훈/folder.jpg
 3979359700 80931 ./data/metadata/People/김/김융희/folder.jpg
+4048988276 50863 ./data/metadata/People/이/이정훈/folder.jpg
```

## Fix

`lib/common.sh` gains three helpers, used by `verify-service.sh`:

| Helper | Purpose |
|---|---|
| `build_checksum_inventory <root> <out> [excludes]` | Builds records `path\tcksum\tbytes` entirely under `LC_ALL=C`, then canonically sorts by path |
| `filter_inventory_excludes <excludes>` | Applies `services.conf` `rsync_excludes` to the source inventory |
| `compare_checksum_inventories <src> <dst> <report>` | Set comparison keyed by path; classifies every difference as MISSING / CHANGED / EXTRA |

Properties:

- **Locale-independent.** Every `sort`, `xargs` and `awk` in the inventory pipeline runs under `LC_ALL=C`, which is a byte-value total order — identical on every filesystem, host and user locale. Both sides are always generated by the same code path, so they cannot diverge in method.
- **Order-independent.** The verdict comes from a path-keyed set comparison, not a positional diff. Line order cannot influence the result at all.
- **Not weakened.** Missing, extra, and content-changed files all still fail the gate. Detection is strictly stronger than before, because differences are now reported *by name* instead of collapsing into one unactionable warning.
- **Fails closed.** If the record count does not match the file count (unreadable file, or a name containing a newline or tab that cannot be represented in the record format), verification fails rather than silently comparing a smaller set.
- **Honours excludes.** Previously the checksum compare ignored `rsync_excludes` entirely, so every deliberately-skipped file looked MISSING — and on NZBGet it tried to checksum the excluded 140 GB tree and hung. Both problems are gone.

### Second defect found and fixed

`run-migration.sh` re-invoked `verify-service.sh` with the same flags as the *post-start* smoke step. Once the service is running on its new config path it immediately writes logs and caches there, so that second full source↔destination compare measures live divergence, not copy fidelity — a guaranteed late-stage false failure. A `--smoke-only` mode now reports container state only. The pre-start copy gate is unchanged and cannot be skipped by this path.

## Regression test

`scripts/migration/tests/test-checksum-verify.sh` — 24 assertions, no external dependencies:

```console
$ ./scripts/migration/tests/test-checksum-verify.sh
passed=24 failed=0
```

Coverage:

| Area | Assertions |
|---|---|
| Identical trees with Hangul, Kana/kanji, accented Latin, Cyrillic, emoji, spaces, NFC/NFD names | compare clean; one record per file |
| Locale independence | inventory byte-identical under `en_US.UTF-8` and `C`; platform collation tie asserted so the test keeps its teeth |
| Ordering immunity | unsorted inventories compare clean; **exact Jellyfin fixture** — the two swapped Hangul records — fails `diff -q` but passes the set comparison |
| Real corruption still caught | missing file, extra file, same-size content change, truncation — each detected **and named** in the report |
| Excludes | excluded files not misreported as missing; a genuinely missing non-excluded file still detected |
| Fail-closed | newline in filename and tab in filename both flagged unverifiable |

The fixture in the "ordering immunity" group is the actual Phase 11 failure, so this specific bug cannot silently return.

## Re-verification of Jellyfin

Re-ran against the staged copy at `/mnt/monarch/appdata/jellyfin`:

```
INFO: Inventory records: source=48101 dest=48104
WARN: Checksum mismatch: missing=2 changed=4 extra=5 matched=48095
```

**The Unicode false positive is gone** — all 48,095 common files, including the entire Hangul/Kana `People` metadata tree, match. The 11 remaining differences are **not** copy defects; they are live drift caused by restarting Jellyfin on the source after the aborted attempt:

| Class | Files | Explanation |
|---|---|---|
| CHANGED | 3 × `data/data/ScheduledTasks/*.js` | Task last-run state rewritten by the running service |
| CHANGED | `log/log_20260731.log` | Today's log, still being appended on the source |
| EXTRA | 5 × `.temp/jellyfin/skia_*.jpg` | Image-scaling temp files present at copy time, since cleaned up on the source |
| MISSING | `data/transcodes/.jellyfin-transcode`, `log/.jellyfin-log` | Zero-byte marker files recreated by Jellyfin at startup |

Zero Unicode paths appear in the difference list. A stale snapshot cannot pass against a live source by definition; completing the cutover requires a fresh delta copy taken with the container stopped.

## Note for the next migration re-run

`copy-config.sh` runs `rsync -aHAX` **without** `--delete`. On a *first* copy that is correct and safe. On a *re-run* into a partially-populated target, files deleted from the source since the previous attempt (the 5 `.temp` files above) remain at the destination and the gate correctly reports them as EXTRA. Re-running a previously-aborted migration therefore needs either a mirroring copy or a cleared target. This is a deliberate framework limitation, not a bug — deletion at the destination should stay an explicit operator decision.
